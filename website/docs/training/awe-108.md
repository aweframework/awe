The scheduler module lets AWE launch work on a schedule, run task workflows, and report the results. This page keeps the practical path front and center: enable the module, create a task, choose a launch mode, and only then move into advanced scheduling, dependencies, servers, and calendars.

## Quick path

1. Add the scheduler starter and module configuration.
2. Apply the required database migration modules.
3. Add the scheduler menu entries.
4. Create a task with the task editor.
5. Choose manual, scheduled, file-based or after-other-tasks launch.
6. Add dependencies, servers, and calendars only when the basic flow already works.

## Before you start

You should already be comfortable with:

- the base application structure from [awe-101](/docs/training/awe-101)
- queries and maintains from [awe-104](/docs/training/awe-104)

If you need the exhaustive scheduler field matrix, use the dedicated guides after this tutorial pass:

- [Schedule configuration guide](/docs/guides/schedule-configuration)
- [Dependencies guide](/docs/guides/dependency-task)
- [Quartz documentation](https://www.quartz-scheduler.org/documentation/)

## Step 1: Enable the scheduler module

Add the starter dependency:

```xml title="pom.xml"
<dependency>
  <groupId>com.almis.awe</groupId>
  <artifactId>awe-scheduler-spring-boot-starter</artifactId>
</dependency>
```

Enable the module list entry in your generated app `application.properties` by adding `awe-scheduler` to your existing module list:

```properties title="application.properties"
# Keep the rest of the list aligned with your application.
# The required scheduler addition is awe-scheduler.
awe.application.module-list=<your-existing-modules>,awe-scheduler
```

For example, generated Angular apps usually start from `<your-app>,awe`, while generated React apps include `awe-react` as well. Modules such as `awe-tools` are optional and only belong in this list when your application actually uses them.

Enable the related database migrations:

```properties title="application.properties"
# Enable database update by Flyway
spring.flyway.enabled=true
awe.database.migration-modules=AWE,SCHEDULER,[YOUR_APP]
```

Add the scheduler menu entries:

```xml title="private.xml or public.xml"
<menu screen="home_horizontal" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:noNamespaceSchemaLocation="https://aweframework.gitlab.io/awe/docs/schemas/menu.xsd" context="screen/private/home" default-action="screen">
  <option name="scheduler" label="MENU_SCHEDULER" icon="clock-o">
    <option name="scheduler-activity" label="MENU_SCHEDULER_ACTIVITY" screen="scheduler-activity" icon="lucide:activity">
      <option name="scheduler-flow-run" screen="scheduler-flow-run" invisible="true" />
    </option>
    <option name="scheduler-task-catalog" label="MENU_SCHEDULER_TASK_CATALOG" screen="scheduler-task-catalog" icon="lucide:list-checks">
      <option name="scheduler-task" screen="scheduler-task" invisible="true" />
      <option name="scheduler-task-editor" screen="scheduler-task-editor" invisible="true" />
    </option>
    <option name="scheduler-configuration" label="MENU_SCHEDULER_CONFIGURATION" screen="scheduler-configuration" icon="lucide:settings"/>
  </option>
</menu>
```

### Optional scheduler properties

If you need to change runtime behavior, override the scheduler properties in your configuration.

```properties
#################################################
# Scheduler properties
#################################################
awe.scheduler.tasks-load-on-start=true
awe.scheduler.stored-executions=5

#################################################
# Scheduler thread pool properties
#################################################
awe.scheduler.task-pool.size=20
awe.scheduler.task-pool.max-size=50
awe.scheduler.task-pool.queue-size=1000
awe.scheduler.task-pool.termination=120s

#################################################
# Scheduler log
#################################################
awe.scheduler.execution-log-path=/var/log/my-app/scheduler

#################################################
# Scheduler reporting
#################################################
awe.scheduler.report-email-from-value=scheduler@almis.com
```

If you enable clustered execution, all participating instances must coordinate through the configured datasource.

:::note
Do not run clustered scheduling across machines with unsynchronized clocks. Quartz-based coordination depends on time being consistent enough across the participating nodes.
:::

For deeper Quartz storage details and job store setup, use the official Quartz documentation.

## Step 2: Understand the scheduler model

A scheduler task is a job plus its launch configuration.

In practice, you will work with:

- **tasks**: what to execute and when
- **dependencies**: what should run after a task finishes
- **servers**: where command or file-based work executes
- **calendars**: dates that should be ignored by schedules

Task types:

| Task type | Purpose |
| --- | --- |
| Maintain task | Executes a public maintain with a defined schedule. |
| Command task | Executes a command on the selected server with the defined schedule. |

## Step 3: Create a task with the task editor

Open **Tasks** and press **New task**. The task editor is one page with six sections: a navigation on the left marks
the section in sight and the ones with errors, a summary on the right follows the changes, and **Save** opens the task
page of the new task. The same editor edits and duplicates a task.

| Section | What you set |
| --- | --- |
| What it runs | Name, description and the execution type: a public maintain or a command |
| Parameters | The values the maintain or the command receives |
| When | Manual, scheduled, when a file arrives, after other tasks or webhook |
| Dependencies | Read only: the tasks that run after this one |
| Behaviour | Timeout, executions kept, active, and whether the tasks that run after it are launched on warning or on error |
| Notifications | The report sent when the task ends |

### 1. What it runs and behaviour

| Element | Section | Definition | Use |
| --- | --- | --- | --- |
| Name | What it runs | Task name | **Required** |
| Description | What it runs | Task description | Optional |
| Execute | What it runs | Command or Maintain | **Required** |
| Command | What it runs | Command to launch | Required for command tasks |
| Execution path | What it runs | Folder where the command runs | Optional for command tasks |
| Run on remote server | What it runs | Runs the command on an SSH server instead of on the scheduler host | Optional for command tasks |
| Remote server | What it runs | SSH server that runs the command | Required when remote execution is checked |
| Maintain | What it runs | Maintain to launch | Required for maintain tasks |
| Timeout | Behaviour | Maximum execution time | Optional |
| Executions kept | Behaviour | Number of stored executions used for statistics | Optional |
| Active task | Behaviour | Task status | **Required** |
| Launch dependencies in case of warning | Behaviour | Whether the tasks that run after it continue on warning | Optional |
| Launch dependencies in case of error | Behaviour | Whether the tasks that run after it continue on error | Optional |
| Set execution as warning in case of dependency error | Behaviour | Marks this execution as warning when a dependency ends with an error | Optional |

:::note
To expose a maintain to the scheduler, the maintain must be declared with `public="true"`.
:::

### 2. Parameters

This section defines the execution context passed to the selected maintain or command.

| Element | Definition | Use |
| --- | --- | --- |
| Name | Parameter name | **Required** |
| Source | Where the value comes from | **Required** |
| Type | Parameter type shown to the user | **Required** |
| Value | Literal value or referenced variable name | Optional |

For maintain tasks, the required maintain parameters are usually added automatically.

### 3. When

Choose how the task is launched:

#### Manual

The task runs only when launched by hand: **Run…** in the Tasks catalog or in its task page.

#### Scheduled

The task runs on a repetition: every N minutes or hours, daily, workdays, weekly, monthly, once or custom. A preview
shows its next five runs.

Use this tutorial for orientation, then move to the [schedule configuration guide](/docs/guides/schedule-configuration) for the full schedule options.

#### File

The scheduler periodically checks files and launches work based on the configured file criteria.

Typical fields:

| Element | Definition | Use |
| --- | --- | --- |
| Search at | Server where the file check happens | **Required** |
| File path | Location of the files | **Required** |
| File pattern | Pattern the files must match | **Required** |

The FTP or SSH credentials are not part of the task: they are stored in the server selected in **Search at** (see [Servers](#servers)).

#### After other tasks

The task runs when the tasks you choose as its parents end. See [Step 5](#step-5-add-dependencies-when-the-task-flow-is-stable).

### 4. Dependencies

This section lists, read only, the tasks that run after this one. They are chosen in each of those tasks, in
**When** › **After other tasks**. Go deeper with the [dependencies guide](/docs/guides/dependency-task).

### 5. Notifications

This section configures what happens after the task finishes.

Available report modes:

- **None**: no report
- **Email**: send execution information by email
- **Broadcast**: send a broadcast message to selected users
- **Maintain**: run a maintain as the reporting action

Email example fields:

| Element | Definition | Use |
| --- | --- | --- |
| Send in case of | Allowed final statuses for sending the email | **Required** |
| Email server | Sender configuration | **Required** |
| Send to users | Destination users | **Required** |
| Title | Email title | **Required** |
| Message | Email message | **Required** |

## Step 4: Choose the right schedule depth

For most first uses, you only need to pick the launch model correctly.

### Repetitive schedules

Use these when the task should run every `X` seconds, minutes, hours, days, months, or years.

Common shared fields include:

- calendar
- from / to
- repeat each

The exact field combinations depend on the chosen unit, so use the [schedule configuration guide](/docs/guides/schedule-configuration) when you need the full matrix.

### One-time schedules

Use these when the task should run once at a specific date/time.

### Custom schedules

Use these when Quartz-level control is necessary. This is the most flexible option, but it is also the least tutorial-friendly one, so prefer the dedicated schedule guide when you reach this level.

## Step 5: Add dependencies when the task flow is stable

Dependencies let one task launch other tasks after it finishes.

### Choose the parents in the child

Open the task that must run later, choose **When** › **After other tasks** and pick its parents. With several parents it
runs once, when all of them have ended. A task that would close a loop cannot be chosen.

### The condition belongs to the parent

Whether a parent launches its children on warning or on error is set in the **Behaviour** of the parent, the same for all
its children. The child shows it read only, with a link to the parent.

## Step 6: Configure servers and calendars only when needed

Both live in the **Configuration** screen of the scheduler menu, one tab each, and are edited in a side panel.

### Servers

Servers are mainly used for command execution and file-based task checks. Press **New server** in the **Servers** tab;
**Test connection** checks the values of the form without saving them.

Core fields:

| Element | Definition | Use |
| --- | --- | --- |
| Name | Server name | **Required** |
| Server | Server address | **Required** |
| Port | Server port | **Required** |
| Type of connection | Protocol used to connect (`ftp`, `folder` or `ssh`) | **Required** |
| Active | Server status | **Required** |
| Server user | User for SSH and FTP connections | Optional |
| Server password | Password for SSH and FTP connections | Optional |
| Private key | Private key for SSH connections | Optional |
| Private key passphrase | Passphrase of the private key | Optional |

If a server is inactive, tasks depending on it will not use it.

### Calendars

Calendars define dates that the scheduler should ignore. Press **New calendar** in the **Calendars** tab; its dates
are added in the same side panel (**Add date**, or **Import file** with an `.ics` or `.csv` file).

Basic calendar fields:

| Element | Definition | Use |
| --- | --- | --- |
| Name | Calendar name | **Required** |
| Description | Calendar description | **Required** |
| Active | Calendar status | **Required** |

Each date entry has:

| Element | Definition | Use |
| --- | --- | --- |
| Date | Ignored date | **Required** |
| Name | Human-readable name for the date | Optional |

Each task can be associated with one calendar.
